# 01 - MCJEBooster 版本控制与发布规范

> 英语文档为规范版本；`docs/zh/` 为中文副本。
> 规范借鉴自 Aprism Loader 项目（NDBlockConnect/Aprism）。

**适用范围：** v26.0-Alpha.1 及之后的所有版本。

## 版本号格式

```
v<年>.<minor>[-Alpha.<n>]
```

- **主线（Major line）** — 每个日历年一条。`v26` 为 2026 线，包含十个 minor：
  `v26.0` ... `v26.9`。
- **开发阶段（公开）** — 每个 minor 内，`v26.0-Alpha.1` ... `v26.0-Alpha.9`
  以 GitHub **Pre-Release** 形式发布。常规节奏为每两周一个 Alpha；
  密集开发窗口期可压缩节奏。
- **候选版本** — `Alpha.9` 即发布候选版（RC）。**永远不会有 Alpha.10。**
- **minor 正式版** — 裸版本号（如 `v26.0`）是该 minor 的正式 GA **Release**。
- **Beta** — 不在计划内。
- **接口契约** — 版本号只增不减；允许带废弃声明的弃用。

## 标签与产物

| 项目 | 格式 | 示例 |
|---|---|---|
| Git 标签 | 与版本号一致 | `v26.0-Alpha.1`、`v26.0` |
| JAR 产物 | `MCJEBooster-<版本号>.jar` | `MCJEBooster-v26.0-Alpha.1.jar` |
| 校验和 | `checksums.txt`（SHA-256），每个产物一条 | — |

每次发布都附带 SHA-256 `checksums.txt`，运行前请校验：

```bash
sha256sum -c checksums.txt
```

## 发布类型

| 版本形态 | GitHub 发布类型 |
|---|---|
| `v26.x-Alpha.n` | Pre-Release（预发布） |
| `v26.x`（裸版本号） | Release（正式发布） |

## 提交信息规范

```
<type>(<scope>): v<版本> - <摘要>（<细节>；<测试数>）
```

- **type** ∈ `feat`、`fix`、`refactor`、`chore`、`release`、`docs`、`test`
- **scope** — 模块或关注点，如 `lowlevel`、`client`、`hybrid`、`repo`、`ci`
- 功能提交需携带目标版本号与测试计数（如 `10 tests, 42 total`）；
  发布提交使用 `release: <版本>`。

本仓库示例：

```
feat(repo): v26.0-Alpha.1 - central version constant + deterministic build
feat(client): v26.1-Alpha.1 - client-side detection seam (SideDetector; 6 tests, 30 total)
release: v26.0
```

## 唯一版本源

运行时版本字符串只存在于一个位置：
`com.mcjebooster.util.BoosterVersion.VERSION`。修改它，用
`scripts/build.sh` 重新构建，打标签，然后发布。
其他任何文件不得硬编码不同的发布版本号。

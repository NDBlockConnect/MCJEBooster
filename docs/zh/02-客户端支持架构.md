# 02 - 客户端支持架构（混合 Aprism 方案）

> 英语文档为规范版本；`docs/zh/` 为中文副本。
> 状态：于 v26.0-Alpha.8 接受设计，在 v26.1 系列中实现。

## 1. 问题陈述

在 v26.0 线之前，MCJEBooster **只支持服务端**：

- `MinecraftServerTransformer` 只匹配 `MinecraftServer` /
  `DedicatedServer` 类及其 tick 方法。
- `InjectionBridge.tickRegions(Object)` 预期一个专用服务器风格的对象，
  可访问其世界（levels）、实体和方块实体。
- 外部注入器与 Agent 均在专用服务器进程上验证。

客户端进程是另一回事：

| 关注点 | 专用服务器 | 客户端 |
|---|---|---|
| 类加载器拓扑 | `-jar` 系统类加载器 | 各启动器不同（官方、HMCL、PCL2、MultiMC/Prism、CurseForge……） |
| 入口点 | `MinecraftServer.run()` | `net.minecraft.client.main.Main` → 渲染器 + 内置服务器 |
| Tick 所有权 | 单一服务器线程 | 渲染线程 +（单人游戏）内置服务器线程 |
| 混淆 | Mojang/proguard | Mojang/proguard + 加载器重映射 |
| 第三方干扰 | 较少 | OptiFine、性能模组、覆盖层、防篡改工具 |

## 2. 为什么纯独立客户端注入不可靠

用原生 Attach API 附加到客户端 JVM *可行*，但：

1. 每个启动器的类路径组装方式不同；为服务器调优的类加载器探测在
   客户端布局下会失效。
2. 没有生命周期契约——Agent 可能在客户端类加载之前或之后落地，
   也没有"游戏完全启动"的回调。
3. 不与其他转换器（Mixin、OptiFine）协调，转换顺序冲突未定义。
4. 在*纯联机*客户端上，可优化的对象是渲染与区块管线，而不是
   tick 循环——在那里盲目注入 tick 钩子既无用又危险。

## 3. Aprism v26.1-Alpha.8 提供了什么

Aprism Loader（同组织的姊妹项目）在 `v26.1-Alpha.8` 中交付了
**底层 API 基础**，注释中明确称其为 *"MCJEBooster layer"*：

```java
package com.aprism.loader.lowlevel;

public final class ClassRedefiner {
    public ClassRedefiner(Instrumentation instrumentation);
    public boolean isRedefineSupported();
    public boolean isRetransformSupported();
    public boolean redefine(Class<?> target, byte[] newBytes);  // 容错
    public int retransform(Class<?>... targets);                // 返回成功数量
}

public final class MethodHookRegistry {
    public static String hookKey(String className, String methodName, String descriptor);
    public static void register(String className, String methodName, String descriptor, Runnable listener);
    public static void unregister(String className, String methodName, String descriptor, Runnable listener);
    public static boolean hasAnyHookForClass(String className);
    public static boolean hasHook(String className, String methodName, String descriptor);
    public static void fire(String hookKey);   // 异常被吞掉，绝不崩溃游戏
    public static void clear();
}

public final class MethodHookTransformer extends ClassVisitor { /* 方法入口钩子注入 */ }
```

Aprism 同时补齐了客户端所需的脚手架：

- 经过验证的 `javaagent` 引导，带 `side=client|server`、`gameRoot`、
  `mcVersion` 参数和两阶段生产引导。
- `IAprismMod` 生命周期（`PREINIT/INIT/SETUP/COMPLETE`，外加
  `CLIENT`/`SERVER` 端阶段）。
- 用于即放即用分发的 `.aje` 包格式与清单契约。

## 4. 权衡分析

| 方案 | 稳定性 | 独立使用 | 工作量 | 结论 |
|---|---|---|---|---|
| A. 仅原生客户端附加 | 低（逐启动器脆弱） | 可以 | 低 | 不够 |
| B. 纯 Aprism 扩展（`.aje`） | 高 | 否——必须装 Aprism | 中 | 过于排他 |
| C. **混合**：独立内核 + 可选 Aprism 桥 | Aprism 在场时高，其余场景不变 | 可以 | 中 | **选定** |

### 混合契约

1. MCJEBooster 保持独立 Agent/注入器——专用服务器用户零破坏。
2. 新增 `SideDetector`，从已加载类、系统属性和内置服务器存在性判定
   `SERVER | CLIENT_INTEGRATED | CLIENT_MULTIPLAYER | UNKNOWN`。
3. 当 MCJEBooster 检测到运行在 **Aprism Agent 内部**（系统属性
   `aprism.agent.active=true` 或 Aprism 类可加载）时，切换为
   **Aprism 桥模式**：
   - 钩子经由 `MethodHookRegistry.register(...)` 注册，而非原生插桩；
   - 重定义经由 `ClassRedefiner` 完成；
   - 初始化对齐 Aprism 生命周期阶段。
   桥以**反射方式**访问（编译期可选），独立 jar 永不依赖 Aprism 产物。
4. 无 Aprism 时回退经典独立路径。此时客户端可用的能力：
   单人游戏的内置服务器优化（复用服务器管线）；
   纯联机客户端为安全的测量模式。
5. 模式选择：`mcjebooster.mode=auto|standalone|aprism`（默认 `auto`）。
   客户端 tick 并行**默认关闭**（`experimental.parallelTick=false`），
   与服务端行为一致。

## 5. v26.1 的客户端范围

| 场景 | v26.1 行为 |
|---|---|
| 专用服务器 | 不变（服务器管线） |
| 单人客户端（内置服务器） | 服务器管线作用于内置服务器 |
| 联机客户端 | 检测 + 指标 + 钩子接缝；不修改 tick |
| Aprism 下的客户端 | 桥模式；钩子经 Aprism 注册表注册 |

渲染线程与区块网格优化在 v26.1 **明确不做**（接缝验证后作为
v26.2+ 的候选）。

## 7. 决策记录

**ADR-006：经 Aprism 桥的混合客户端支持**
- 日期：2026-08-10
- 决策：采用方案 C（混合），Aprism 集成走反射
- 理由：Aprism v26.1-Alpha.8 的底层 API 正是为此层而生；
  独立行为不得退化；反射桥让 LGPL 产物保持零依赖。
- 否决的备选：A（脆弱）、B（强制所有用户安装 Aprism）。
